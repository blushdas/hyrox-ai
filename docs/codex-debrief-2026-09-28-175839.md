## Original Goal
Return an authenticated Safari user to FINISHER through a short-lived single-use code, exchange it for a separate native bearer session, and persist that session in iOS Keychain without changing existing web auth.

## What Was Implemented
The Worker can convert a signed-in web session into a random code valid for exactly 60 seconds. D1 stores only its SHA-256 hash. One atomic UPDATE consumes it, then the exchange endpoint returns a 30-day Auth.js encrypted token with a dedicated native salt. The session endpoint re-reads the user from D1. Both native API routes have exact-origin CORS and generic authentication failures with no-store responses.

The app exchanges an incoming finisher://auth code, writes its token to Keychain, and navigates to the dashboard. Protected native screens read that token and send it in Authorization with cookies explicitly omitted. Native sign-out removes the Keychain token. Keychain errors propagate; no web-storage fallback is allowed. The iOS build excludes the new server routes and rejects an absent or non-HTTPS auth origin before touching the existing export.

Dependency: exactly one direct npm dependency, @aparajita/capacitor-secure-storage@8.0.1. Its published source explicitly targets Capacitor 8 and uses iOS Keychain; installed Package.swift depends on capacitor-swift-pm >=8.0.0 and KeychainSwift >=21.0.0. Tokens use whenUnlockedThisDeviceOnly and sync=false. Source: https://github.com/aparajita/capacitor-secure-storage ; evidence: docs/qa/finisher-native-auth-handoff-2026-09-28/plugin.txt. Capacitor sync linked the plugin into the native Swift package.

Evidence-driven adjustment within the sign-in edit target: the inherited GET /api/auth/signin/google URL is unsupported by installed Auth.js v5 and returned 302 to /sign-in?error=Configuration. See docs/qa/finisher-native-auth-handoff-2026-09-28/native-start-original.txt and node_modules/@auth/core/lib/pages/index.js, signin(providerId). Native buttons now open the existing hosted /sign-in?callbackUrl=%2Fauth%2Fnative-complete page. The user selects a provider again there; the unchanged web signIn path performs its normal CSRF-protected POST and preserves the relative native completion callback. This adds one browser selection, avoids changing web auth configuration/API behavior, and fixes an otherwise broken launch path. The original non-native signIn call remains unchanged.
